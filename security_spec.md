# Security Specification for American Institute

## Data Invariants
1. A student document must be owned by the authenticated user (uid matches).
2. `uniqueId` can only be generated by the system (simulated as after payment).
3. `isPaid` can only be transitioned to `true` via a valid payment sequence.
4. Aadhaar and PAN numbers must be strictly validated.

## The Dirty Dozen Payloads
1. Create a student document with a different user's UID.
2. Update `isPaid` to `true` without a payment transaction ID.
3. Update `uniqueId` manually from the client.
4. Read another student's ID card data.
5. Inject a 1MB string into the `name` field.
6. Create a document without a required field like `idNumber`.
7. Use an invalid `idType` like "Passport".
8. Update `createdAt` after the document is created.
9. List all students in the database.
10. Delete a student document that they don't own.
11. Update `email` to an email they don't own.
12. Creating a document with a non-Verhoeff compliant Aadhaar number (this is handled at the application layer, but rules will enforce size/type).

## Rules Generation Strategy
- Master Gate on `/students/{uid}`.
- `isValidStudent` helper for creation and updates.
- Split update actions for "Update Profile" vs "Complete Payment".
